# hCaptcha Integration Guide

This document explains how hCaptcha is integrated into the application,
how the keys are configured, and how the CAPTCHA mechanism behaves in
development mode.

The goal is to provide a clear and reproducible setup for reviewers,
developers, and security auditors.

---

## 1. What is hCaptcha?

hCaptcha is a bot protection service that helps distinguish human users
from automated scripts by analyzing user behavior and, if necessary,
requiring a visual challenge.

---

## 2. Creating an hCaptcha Account

To use hCaptcha, you must first create an account:

1. Go to the official hCaptcha website  
    https://www.hcaptcha.com/

2. Create a free account.

3. Access the **Dashboard** after logging in.

---

## 3. Generating hCaptcha Keys

Once logged in to the dashboard:

1. Click on **“Add Site”**.
2. Choose a site name (for example: `SecureSoftwareProject`).
3. Select the appropriate behavior settings.
4. hCaptcha will generate two keys:
   - **Site Key** (public key)
   - **Secret Key** (private key)

### Key Roles

| Key Type   | Description |
|-----------|-------------|
| Site Key  | Used on the client side (HTML / frontend) |
| Secret Key | Used on the server side to verify the CAPTCHA response |

 **Important:**  
The keys generated by default are **development / test keys** and must
**not** be used in production.

---

### Setting Up Keys for Local Development

1. **Secret Key (server-side)**  
   Export your secret key as an environment variable before starting the server:

   ```bash
   export HCAPTCHA_SECRET=<YourSecretKeyHere>
   ```

The server will read this value from the environment and use it to verify CAPTCHA responses.

2. **Site Key (frontend / client-side)**
  The site key is currently hard-coded in the frontend HTML/JS:
  ```bash
  ES_c9ae3ffa82634ff7962a44c665c18023
  ```
  
You must replace this key with your new site key generated for your site.

## 4. Development vs Production Keys

### Development / Test Keys

In this project, we intentionally use **development keys** in order to:

- simplify local testing;
- avoid exposing real production credentials;
- demonstrate CAPTCHA behavior in a controlled environment.

For development purposes, the following option is enabled:

- **Always Challenge**

This forces hCaptcha to always display the visible challenge,
even if the invisible CAPTCHA score is high.

 This is useful for:
- demonstration purposes;
- validation of the fallback mechanism;
- security testing.

### Production Keys

For a real production deployment:

1. Go to the hCaptcha dashboard.
2. Register the real domain name.
3. Generate **production keys**.
4. Disable **Always Challenge**.
5. Let the invisible CAPTCHA handle most cases automatically.

---

## 5. How hCaptcha Works in This Project

The CAPTCHA mechanism is implemented as a **two-layer defense**:

### Layer 1: Invisible CAPTCHA

- Runs silently in the background.
- Analyzes user behavior (mouse movements, timing, browser signals).
- Produces a confidence score.

If the score is high, the request is accepted without user interaction.

### Layer 2: Visible CAPTCHA (Fallback)

- Triggered when the score is too low or when *Always Challenge* is enabled.
- Requires explicit user interaction.
- Confirms that the requester is a human.

---

## 6. Server-Side Verification (Important)

hCaptcha must **always** be verified on the server side.

Workflow:
1. The client sends the CAPTCHA token to the backend.
2. The backend sends the token and the **Secret Key** to hCaptcha’s verification API.
3. hCaptcha responds with a validation result.
4. The request is accepted or rejected based on this result.

 Client-side validation alone is **not secure**.

---

## 7. Security Considerations

- hCaptcha does **not replace authentication** mechanisms such as WebAuthn.
- It acts as a **pre-authentication filter** against bots and automation.
- CAPTCHA reduces attack surface but does not eliminate all threats.
- Advanced attackers may still use CAPTCHA farms or human solvers.

---

## 8. Summary

- hCaptcha is used to protect sensitive entry points.
- Development keys are used for testing and demonstration.
- Always Challenge is enabled in development to validate the fallback layer.
- Production deployment requires dedicated production keys.
- CAPTCHA is part of a layered security approach.
